## 1. หลักการออกแบบและขอบเขต

### 1.1 หลักการที่ยึดตลอดโปรเจกต์

| # | หลักการ | ผลต่อการตัดสินใจ |
|---|---|---|
| P1 | **ไม่ใช่เว็บขายของ** | ไม่มีตะกร้า ไม่มีชำระเงิน ไม่แสดงราคาต่อสาธารณะ ทุกเส้นทางจบที่ "ทักไปคุยกับร้าน" |
| P2 | **เครื่องมือต้องมีประโยชน์แม้ไม่ซื้อของ** | ปฏิทินดูแลต้องใช้ได้กับต้นไม้ที่ซื้อมาจากที่อื่นด้วย ไม่ล็อกว่าต้องซื้อจากร้าน |
| P3 | **Guest-first** | ทุกฟีเจอร์อ่านอย่างเดียวใช้ได้โดยไม่ต้องสมัคร บังคับสมัครเฉพาะตอนต้องเก็บข้อมูลข้ามเครื่อง |
| P4 | **ร้านต้องไม่ต้องเรียนของใหม่** | Phase 1 ตอบผ่าน LINE ตัวเดิม หลังบ้านมีแค่หน้าเดียวที่ต้องใช้เป็นประจำ |
| P5 | **ต้นทุนผันตามจำนวนคนใช้ ไม่ใช่จำนวนฟีเจอร์** | ทุกฟีเจอร์ที่มีค่าใช้จ่ายต่อครั้งต้องมี quota + เพดานงบ + kill switch |
| P6 | **ของจริงจากร้านคือจุดต่าง** | ห้ามใช้รูปจากอินเทอร์เน็ต ข้อมูลการดูแลต้องผ่านการยืนยันจากที่บ้าน |
| P7 | **ไทยเป็นค่าเริ่มต้น** | ฤดูกาลไทย 3 ฤดู, ชื่อเล่นภาษาไทย, หน่วยนิ้ว/กระถาง, LINE เป็นช่องทางหลัก |

### 1.2 นอกขอบเขต (Non-goals) — ระบุชัดเพื่อกันงานบานปลาย

- ระบบตะกร้า / ชำระเงินออนไลน์ / ระบบขนส่ง — **ไม่ทำทุก phase**
- ระบบสต็อกแบบนับจำนวนจริง — ใช้แค่สถานะ 3 ระดับ (มี / สั่งได้ / ตามฤดูกาล)
- บัญชี/การเงินของร้าน
- แอปสำหรับพนักงานร้านแยกต่างหาก
- รองรับหลายภาษา (i18n เตรียมโครงไว้ แต่ Phase 1–3 มีแต่ภาษาไทย)

### 1.3 นิยามศัพท์

| คำ | ความหมายในเอกสารนี้ |
|---|---|
| **Species (พันธุ์)** | ข้อมูลกลางของต้นไม้ 1 ชนิด เช่น "มอนสเตอร่าด่าง" — ร้านเป็นคนดูแลข้อมูลนี้ |
| **UserPlant (ต้นของฉัน)** | ต้นไม้ 1 ต้นที่ผู้ใช้มีจริง ผูกกับ species 1 ตัว มีชื่อเล่น กระถาง ตำแหน่งของตัวเอง |
| **CareTemplate** | สูตรการดูแลมาตรฐานของ species (ร้านตั้ง) — ระบบเอาไปคำนวณเป็นตารางจริงของผู้ใช้ |
| **CareTask** | งานดูแล 1 ครั้งที่ครบกำหนด เช่น "รดน้ำมอนสเตอร่า 5 ก.ย." |
| **Inquiry** | 1 ครั้งที่ผู้ใช้กด "ถามร้าน" — ตัวชี้วัดหลักของโปรเจกต์ |
| **Handoff** | การส่งต่อบทสนทนาจาก AI ไปให้คนที่ร้านตอบ |

### 3.2 Tech stack และเหตุผล

| ชั้น | เลือกใช้ | เหตุผล |
|---|---|---|
| Framework | **Next.js (App Router)** | SSR ทำให้ Google เก็บหน้าต้นไม้ไปติดอันดับได้ — ข้อได้เปรียบหลักเหนือแอป |
| Hosting | **Vercel** (Fluid Compute) | แผนฟรีพอสำหรับ Phase 1, deploy อัตโนมัติ, preview ทุก commit |
| Database | **Postgres (Neon ผ่าน Vercel Marketplace)** | ฟรีระดับเริ่มต้น, มี full-text search ในตัว, ไม่ต้องเพิ่มบริการค้นหาแยก |
| ORM | **Drizzle** | schema เป็น TypeScript, migration ตรงไปตรงมา |
| รูปภาพ | **Vercel Blob** + `next/image` | แปลงเป็น WebP/AVIF อัตโนมัติ ลดค่า bandwidth |
| Auth | **LINE Login เป็นหลัก** + อีเมล/รหัสผ่านสำรอง | ลูกค้าไทยมี LINE อยู่แล้ว ลดแรงเสียดทานตอนสมัครมากที่สุด และได้ `userId` ไว้ส่งแจ้งเตือน LINE ต่อ |
| แจ้งเตือน | **Web Push (VAPID)** + **LINE Messaging API** | Web push ฟรี; LINE เป็นตัวสำรองครอบคลุม iPhone ที่ไม่ได้ Add to Home Screen |
| PWA | manifest + service worker | ให้ Add to Home Screen ได้ และเป็นฐานของ Phase 3 |
| CSS | **Tailwind CSS** | เขียนเร็ว, bundle เล็ก |
| AI (Phase 2) | **Vercel AI Gateway** | สลับผู้ให้บริการได้โดยไม่แก้โค้ด + เห็นค่าใช้จ่ายรวมที่เดียว + ตั้งเพดานงบได้ |
| Analytics (Phase 3) | ตาราง `events` ของตัวเอง + Vercel Analytics | ข้อมูลอยู่กับเรา ไม่ต้องจ่าย SaaS |

### 3.3 หลักการทางเทคนิคที่ยึด

1. **Server Components เป็นค่าเริ่มต้น** — ใช้ Client Component เฉพาะส่วนที่ต้อง interact จริง (ฟิลเตอร์ ปุ่มบันทึก แชท)
2. **ไม่มี state ฝั่ง server ที่ค้างข้ามคำขอ** — ทุกอย่างอยู่ใน DB
3. **Idempotent cron** — งานตามเวลารันซ้ำแล้วต้องไม่สร้างงานซ้ำ (ใช้ unique key `user_plant_id + task_type + due_date`)
4. **ไม่มี secret ฝั่ง client** — คีย์ AI, LINE token อยู่ฝั่ง server เท่านั้น
5. **ทุกการเรียก AI ผ่าน service เดียว** (`lib/ai/`) ที่บังคับ quota + budget cap ก่อนยิงจริงเสมอ

## 5. Care Schedule Engine — หัวใจของระบบ

นี่คือส่วนที่ทำให้เว็บนี้ต่างจาก "หน้าข้อมูลต้นไม้ทั่วไป" ถ้าส่วนนี้แม่น ผู้ใช้จะกลับมาทุกสัปดาห์ ถ้าไม่แม่น เขาจะปิดแจ้งเตือนแล้วหายไป

### 5.1 หลักคิด

ร้านตั้งค่ากลางไว้แค่ **"ปกติรดทุกกี่วัน"** ต่อฤดู แล้วระบบปรับตามสภาพจริงของผู้ใช้ 3 อย่าง: **วัสดุกระถาง · ขนาดกระถาง · ตำแหน่งที่วาง** ผู้ใช้ไม่ต้องกรอกอะไรยาก แต่ผลลัพธ์ต่างกันจริง (ต้นเดียวกันในกระถางดินเผาที่ระเบียงแดด กับในกระถางเคลือบในห้องแอร์ ห่างกันได้เท่าตัว)

### 5.2 ฤดูกาลไทย

| ฤดู | เดือน | ใช้ค่า |
|---|---|---|
| ร้อน | มี.ค. – พ.ค. | `water_days_hot` |
| ฝน | มิ.ย. – ต.ค. | `water_days_rainy` |
| หนาว/แล้ง | พ.ย. – ก.พ. | `water_days_cool` |

*(นี่คือรายละเอียดที่แอปต่างชาติทำไม่ได้ เพราะมันคำนวณจากฤดูแบบ 4 ฤดูของซีกโลกเหนือ)*

### 5.3 ตัวคูณปรับค่า

```
interval = base_days(season)
         × pot_material_factor
         × pot_size_factor
         × placement_factor
```

| ปัจจัย | ค่า | ตัวคูณ | เหตุผล |
|---|---|---|---|
| **วัสดุกระถาง** | ดินเผา | ×0.80 | ระเหยผ่านผนังกระถาง แห้งเร็ว |
| | พลาสติก / กระถางแขวน | ×1.00 | ค่ามาตรฐาน |
| | เซรามิกเคลือบ / ปูน | ×1.15 | ไม่ระบายน้ำ ชื้นนาน |
| **ขนาดกระถาง** | < 6 นิ้ว | ×0.85 | ดินน้อย แห้งเร็ว |
| | 6–10 นิ้ว | ×1.00 | |
| | > 10 นิ้ว | ×1.20 | ดินเยอะ อุ้มน้ำนาน |
| **ตำแหน่ง** | กลางแจ้งแดดเต็ม | ×0.70 | |
| | ระเบียง/มีร่มรำไร | ×0.90 | |
| | ในบ้านใกล้หน้าต่าง | ×1.00 | |
| | ในบ้านห่างหน้าต่าง | ×1.25 | |
| | ห้องแอร์ | ×1.20 | แอร์ดูดความชื้นแต่ไม่มีแดด สุทธิแล้วชื้นนานกว่า |

**กติกาปิดท้าย**
- ปัดเป็นจำนวนเต็มวัน (`Math.round`)
- บีบให้อยู่ในช่วง **1–30 วัน** เสมอ
- ถ้าผู้ใช้ตั้ง `custom_water_days` เอง → ใช้ค่านั้นตรง ๆ ไม่คูณอะไรทั้งสิ้น
- ปุ๋ย: ข้ามเดือนที่อยู่ใน `fertilize_pause_months` (พันธุ์ส่วนใหญ่งดปุ๋ยช่วงพักตัว)
- เปลี่ยนกระถาง: นับจาก `acquired_at` หรือครั้งล่าสุดใน `care_logs` แล้วเตือนล่วงหน้า 14 วัน

### 5.4 ตัวอย่างคำนวณจริง

> **มอนสเตอร่าด่าง** · ฤดูฝน base = 6 วัน · กระถางเซรามิกเคลือบ 12 นิ้ว · ในบ้านห่างหน้าต่าง
> `6 × 1.15 × 1.20 × 1.25 = 10.35` → **รดทุก 10 วัน**

> **ต้นเดียวกัน** · ฤดูร้อน base = 4 วัน · กระถางดินเผา 5 นิ้ว · ระเบียงมีร่ม
> `4 × 0.80 × 0.85 × 0.90 = 2.45` → **รดทุก 2 วัน**

หน้าจอจะอธิบายให้ผู้ใช้เห็นด้วยว่าทำไมได้เลขนี้ — สร้างความเชื่อถือมากกว่าโยนตัวเลขมาเฉย ๆ

### 5.5 การเลื่อนรอบเมื่อบันทึกการดูแล

- กด "รดแล้ว" วันนี้ → task ปัจจุบัน `done`, สร้าง task ถัดไป `due = today + interval`
- **รดก่อนกำหนด** (เช่น ครบวันที่ 10 แต่รดวันที่ 8) → นับใหม่จากวันที่ 8 ไม่ใช่วันที่ 10 (ผู้ใช้ถูกเสมอ)
- **รดช้ากว่ากำหนด** → นับใหม่จากวันที่ทำจริงเช่นกัน แต่ถ้าเลยกำหนดเกิน 2 เท่าของรอบ ให้ระบบถามว่า "รอบนี้ยาวไปไหม อยากปรับเป็นทุก N วันไหม" — เรียนรู้จากพฤติกรรมจริง
- **เลื่อน (snooze)** → +1 วัน สูงสุด 3 ครั้งติดต่อกัน แล้วบังคับให้ตอบว่า done/skip
- **ข้าม (skip)** → ไม่สร้าง log แต่สร้าง task รอบถัดไปตามปกติ

### 5.6 งานตามเวลา (Cron)

| งาน | เวลา (Asia/Bangkok) | ทำอะไร |
|---|---|---|
| `generate-tasks` | 03:00 ทุกวัน | สร้าง `care_tasks` ล่วงหน้า 14 วันสำหรับทุก `user_plants` ที่ active (idempotent ด้วย unique key) |
| `send-reminders` | 07:30 ทุกวัน | รวมงานที่ครบกำหนดวันนี้ของแต่ละคนเป็น **ข้อความเดียว** ("วันนี้มี 3 ต้นถึงรอบรดน้ำ") แล้วส่ง Web Push + LINE |
| `season-recalc` | วันที่ 1 ของ มี.ค. / มิ.ย. / พ.ย. | คำนวณรอบใหม่ตามฤดูที่เปลี่ยน และแจ้งผู้ใช้ว่า "เข้าหน้าฝนแล้ว ปรับรอบรดน้ำให้ห่างขึ้น" |

- ส่งวันละไม่เกิน 1 ครั้ง ต่อ 1 คน (รวมทุกต้นเป็นข้อความเดียว) — กันคนรำคาญแล้วปิดแจ้งเตือน

- ถ้าไม่มีงานวันนี้ → ไม่ส่งอะไรเลย (ไม่ส่ง "วันนี้ไม่มีอะไรทำ")
- LINE ส่งเฉพาะกรณี: ผู้ใช้เปิด `notify_line` **และ** (ไม่ได้เปิด web push หรือ web push ส่งไม่สำเร็จ) — ประหยัดโควตาข้อความ LINE

### 6.3 `/plants/[slug]` หน้ารายละเอียดต้นไม้

โครงหน้า (บนลงล่าง)
1. **แกลเลอรีรูปจริง** — รูปแรกเป็น `is_primary` มีป้าย "ถ่ายที่ร้าน" กำกับ
2. **ชื่อ** — ไทย / อังกฤษ / วิทยาศาสตร์ (ตัวเอน) + ชื่อเล่นที่คนเรียก
3. **ป้ายสถานะของ** — สีเขียว "มีที่ร้าน" / สีเหลือง "สั่งได้ ~7–14 วัน" / สีเทา "ตามฤดูกาล"
4. **การ์ดสรุป 6 ช่อง** — แสง · น้ำ · ที่วาง · ความยาก · สัตว์เลี้ยง · ขนาดโตเต็มที่ (ไอคอน + ข้อความ)
5. **วิธีดูแล** — รดน้ำ · ดิน · ปุ๋ย · เปลี่ยนกระถาง (ดึงจาก `care_templates` แสดงเป็นภาษาคน ไม่ใช่ตัวเลขดิบ: "หน้าฝนรดทุก 5–7 วัน หน้าร้อนทุก 3–4 วัน")
6. **"ที่ร้านบอกว่า"** — `shop_note` ในกล่องที่ออกแบบให้เด่น **นี่คือของที่ลอกไม่ได้**
7. **ปัญหาที่พบบ่อย** — accordion จาก `species_problems`
8. **ต้นที่ใกล้เคียง** — 4 พันธุ์ที่ light + water_need + placement ตรงกัน
9. **ปุ่มลอยติดล่างจอตลอด** — [ ถามร้านเรื่องต้นนี้ ] และ [ + เพิ่มเข้าสวนของฉัน ]

**SEO (สำคัญมาก — เป็นเหตุผลหลักที่เลือกทำเว็บ)**
- `<title>`: `{name_th} ({name_en}) วิธีปลูกและดูแล | ชื่อร้าน`
- meta description จาก `summary`
- JSON-LD: `Product` (ไม่มีราคา) + `FAQPage` จาก `species_problems`
- `sitemap.xml` สร้างอัตโนมัติจาก species ที่ published
- รูปทุกใบมี `alt` ภาษาไทย
- URL เป็น slug ภาษาอังกฤษอ่านออก

### 6.4 การส่งต่อไป LINE (Handoff)

**เมื่อกดปุ่ม "ถามร้าน"**

1. สร้างแถวใน `inquiries` → ได้ `ref_code` เช่น `TFL-4K9P`
2. เปิด LINE พร้อมข้อความตั้งต้น
3. บนเดสก์ท็อป: แสดง QR code ของ LINE OA + ข้อความให้กดคัดลอก

**รูปแบบลิงก์**
```
https://line.me/R/oaMessage/@{LINE_OA_ID}/?{encodeURIComponent(message)}
```

**เทมเพลตข้อความ** (แยกตาม intent)

| intent | ข้อความ |
|---|---|
| `price` | `สนใจ "มอนสเตอร่าด่าง" จากหน้าเว็บครับ/ค่ะ ขอทราบราคาและขนาดที่มีหน่อยครับ [TFL-4K9P]` |
| `availability` | `อยากทราบว่า "ยางอินเดียด่าง" ตอนนี้มีของไหมครับ/ค่ะ [TFL-7M2X]` |

### 6.5 บัญชีผู้ใช้

- **LINE Login เป็นปุ่มหลัก** (ปุ่มใหญ่ สีเขียว LINE) — ลูกค้าไทยกดปุ่มเดียวจบ
- อีเมล + รหัสผ่านเป็นทางเลือกรอง
- **ไม่บังคับสมัครจนกว่าจะจำเป็น** — กด "เพิ่มเข้าสวนของฉัน" ตอนเป็น guest ให้เก็บไว้ใน localStorage ก่อน แล้วขอให้ล็อกอินเมื่อจะตั้งแจ้งเตือน
- ตอนล็อกอินครั้งแรก: merge favorites + user_plants จาก localStorage เข้าบัญชีอัตโนมัติ พร้อมข้อความ "ย้ายต้นไม้ 3 ต้นที่บันทึกไว้เข้าบัญชีแล้ว"

### 6.6 `/garden` สวนของฉัน

**หน้ารายการ**
- การ์ดต่อ 1 ต้น: รูป (ที่ผู้ใช้ถ่าย หรือรูปพันธุ์เป็นค่าเริ่มต้น) · ชื่อเล่น · ชื่อพันธุ์ · สถานะรอบถัดไป
- **สถานะแสดงด้วยรูปทรง ไม่ใช่แค่สี** (คนตาบอดสีต้องอ่านออก): `เลยกำหนด 2 วัน` (แดง + ไอคอนอัศเจรีย์) / `วันนี้` (ส้ม + จุดทึบ) / `อีก 3 วัน` (เทา + จุดกลวง)
- ปุ่มลัด "รดแล้ว" บนการ์ดเลย — บันทึกได้ในคลิกเดียวจากหน้ารายการ
- เรียงตามงานที่ใกล้ครบกำหนดที่สุดขึ้นก่อน
- Empty state: "ยังไม่มีต้นไม้ในสวน — เพิ่มต้นแรกเพื่อให้เราช่วยจำรอบรดน้ำให้" + ปุ่ม

**เพิ่มต้นไม้ (4 ขั้น)**
1. เลือกพันธุ์ (ค้นหา) — ถ้าไม่มีในระบบ ให้เลือก "อื่น ๆ" แล้วพิมพ์ชื่อเอง (บันทึกลง `search_misses` ด้วย)
2. ตั้งชื่อเล่น + วันที่ได้มา + ได้มาจากไหน
3. กระถาง: ขนาด (นิ้ว) + วัสดุ — แสดงเป็นภาพให้เลือก ไม่ใช่ dropdown
4. ตำแหน่งที่วาง — 5 ตัวเลือกพร้อมภาพประกอบ

→ จบแล้วแสดง **"ตารางดูแลของต้นนี้"** ทันที พร้อมคำอธิบายว่าคำนวณมายังไง (§5.4)

**หน้าต้นเดียว `/garden/[id]`**
- ปฏิทิน 30 วันข้างหน้า แสดง task แต่ละประเภทด้วยสัญลักษณ์ต่างกัน
- ประวัติการดูแลย้อนหลัง (timeline)
- แก้ไขข้อมูลกระถาง/ตำแหน่ง → คำนวณรอบใหม่ทันทีและบอกว่าเปลี่ยนจากกี่วันเป็นกี่วัน
- ปุ่ม "ถามร้านเรื่องต้นนี้" (intent = `care_help`, แนบชื่อพันธุ์ + อายุที่เลี้ยงมา)
- ปุ่ม archive (ต้นตาย/ให้คนอื่นไป) — ไม่ลบข้อมูล

### 6.7 `/today` งานวันนี้

- รายการงานที่ครบกำหนดวันนี้ + ที่เลยกำหนด รวมทุกต้น
- ปุ่ม "ทำครบทุกอย่างแล้ว" สำหรับคนที่รดรวดเดียว
- ปุ่ม snooze / skip รายตัว
- นี่คือหน้าที่ผู้ใช้จะเข้าบ่อยที่สุด — ต้องเปิดเร็วและกดจบใน 2 วินาที

### 6.8 การแจ้งเตือน

**Web Push**
- ขอ permission **หลังจากผู้ใช้เพิ่มต้นไม้ต้นแรกสำเร็จ** เท่านั้น (ไม่ขอทันทีที่เข้าเว็บ — คนจะกดปฏิเสธ)
- ข้อความ: "วันนี้มี 3 ต้นถึงรอบรดน้ำ 🌿" กดแล้วเข้า `/today` ตรง

**iPhone**
- ตรวจว่าเปิดใน Safari ปกติหรือใน standalone mode
- ถ้าเป็น Safari ปกติ: แสดงคำแนะนำแบบมีภาพ 3 ขั้น "กดปุ่มแชร์ → เพิ่มลงหน้าจอโฮม → เปิดจากไอคอน"
- **ไม่ว่ากรณีใดก็เสนอ LINE เป็นทางเลือกเสมอ** — "หรือให้ส่งเตือนทาง LINE แทนก็ได้"

**LINE**
- ผูกบัญชีอัตโนมัติถ้าล็อกอินด้วย LINE
- ส่งผ่าน Messaging API push message
- ทุกข้อความมีลิงก์กลับเข้าเว็บ + ปุ่ม "รดแล้ว" (quick reply) ให้กดจบใน LINE ได้เลยไม่ต้องเปิดเว็บ

## 7. Phase 2 — ข้อกำหนดฟีเจอร์ AI

### 7.1 หลักการที่ยึดกับ AI ทุกตัว

| # | หลัก | วิธีทำจริง |
|---|---|---|
| A1 | **AI ไม่ใช่ผู้เชี่ยวชาญ ร้านคือผู้เชี่ยวชาญ** | ทุกคำตอบมีทางออกไปหาคนจริงเสมอ |
| A2 | **ห้ามแต่งข้อมูลร้าน** | ราคา สต็อก ขนาด ดึงจาก DB เท่านั้น ห้ามให้โมเดลเดา — ใช้ tool call ไม่ใช่ prompt |
| A3 | **ตอบเป็นข้อความก่อน สร้างภาพทีหลัง** | ภาพแพงกว่าข้อความ ~10 เท่า สร้างเมื่อผู้ใช้ยืนยันเท่านั้น |
| A4 | **มีเพดานเสมอ** | quota ต่อคน + เพดานงบต่อเดือน + kill switch |
| A5 | **บอกความมั่นใจ** | วินิจฉัยต้องบอกว่ามั่นใจแค่ไหน ไม่ฟันธงเมื่อไม่ชัวร์ |

### 7.2 ผู้ช่วยตอบคำถาม (`/assistant`)

**สถาปัตยกรรม: RAG + tool calling**

```
คำถามผู้ใช้
   ↓
ค้นข้อมูลร้านที่เกี่ยวข้อง (pgvector บน species + shop_note + problems + FAQ)
   ↓
ประกอบ prompt: system + ข้อมูลร้านที่ค้นได้ + ประวัติแชท 6 ข้อความล่าสุด
   ↓
เรียกโมเดล (Qwen) พร้อม tools: searchSpecies · getStock · createInquiry · handoffToShop
   ↓
ตอบ + ปุ่มลัด (ดูหน้าต้นนี้ / เพิ่มเข้าสวน / ถามร้าน)
```

**System prompt (โครง)**
```
คุณคือผู้ช่วยของร้าน {ชื่อร้าน} ร้านต้นไม้ในประเทศไทย
- ตอบภาษาไทยแบบเป็นกันเอง สุภาพ กระชับ ไม่เกิน 4 ประโยคต่อคำตอบ
- ใช้ได้เฉพาะข้อมูลใน <ข้อมูลร้าน> ที่ให้มา ห้ามแต่งเพิ่ม
- ห้ามบอกราคาเอง ถ้าถูกถามราคาให้เรียก tool createInquiry แล้วชวนทักร้าน
- คำนึงถึงสภาพอากาศไทย: ร้อนชื้น หน้าฝนมิ.ย.-ต.ค. ฝนตกหนัก แดดแรง
- ถ้าไม่แน่ใจ หรือเป็นเรื่องโรค/แมลงที่รุนแรง ให้เรียก handoffToShop
- ห้ามแนะนำสารเคมีอันตราย หรือปริมาณยาที่เฉพาะเจาะจง
```

**เงื่อนไขส่งต่อร้าน (handoff)** — เกิดขึ้นเมื่อ:
1. ผู้ใช้ถามราคา / ต่อรอง / นัดรับของ
2. ผู้ใช้ขอคุยกับคน
3. โมเดลตอบไม่ได้ 2 ครั้งติด หรือ confidence ต่ำ
4. คำถามเกี่ยวกับโรครุนแรง (รากเน่า / แมลงระบาด)

**เมื่อ handoff**: สรุปบทสนทนาเป็นภาษาไทย ≤ 3 บรรทัด → แนบเข้า `inquiries.payload` → เปิด LINE พร้อมข้อความที่มีสรุปนั้น **ที่บ้านไม่ต้องถามซ้ำ**

**เกณฑ์ยอมรับ**
- ตอบคำถาม 20 ข้อจากลูกค้าจริง ต้องถูกต้องยอมรับได้ ≥ 16 ข้อ (80%)
- ห้ามพูดถึงราคาเป็นตัวเลขเด็ดขาด — ทดสอบด้วย red-team 10 คำถามที่พยายามล่อให้บอกราคา
- เวลาตอบตัวแรก ≤ 2 วินาที (streaming)

```
  2. ขาดธาตุอาหาร (ไนโตรเจน)             มั่นใจ ~น้อย
     ...
⚠ นี่เป็นการประเมินเบื้องต้นจากรูป ไม่ใช่การวินิจฉัยที่แน่นอน
[ ส่งรูปนี้ให้ร้านดู ]   [ บันทึกลงประวัติต้นนี้ ]
```

**ข้อกำหนด**
- แสดงความมั่นใจเป็น **คำ** (มาก/ปานกลาง/น้อย) ไม่ใช่ % — เปอร์เซ็นต์ทำให้คนเชื่อเกินจริง
- ถ้าความมั่นใจสูงสุด < เกณฑ์ → ไม่แสดงผลวินิจฉัย แต่แสดง "รูปนี้ดูยาก ส่งให้ร้านดูดีกว่า" + ปุ่ม LINE
- มีคำเตือนความรับผิดทุกครั้ง ไม่ซ่อน ไม่ย่อ
- ปฏิเสธรูปที่ไม่ใช่ต้นไม้ (คน สัตว์ เอกสาร) — ตอบว่า "รูปนี้ไม่ใช่ต้นไม้"
- บันทึกผลลง `diagnoses` และผูกกับ `user_plants` ได้ → เกิดประวัติสุขภาพของต้น

### 7.4 ออกแบบมุมสวนด้วยภาพ (`/design`)

**นี่คือฟีเจอร์ที่แพงที่สุดและเป็นหน้าตาของโปรเจกต์ — ต้องคุมทั้งคุณภาพและต้นทุน**

**ขั้นตอน**
1. อัปโหลดรูปพื้นที่จริง (ระเบียง / หน้าบ้าน / มุมห้อง)
2. **แตะจุดบนรูปเพื่อบอกว่าอยากวางต้นไม้ตรงไหน** (เก็บพิกัดลง `mask_points`)
3. เลือกสไตล์: เขตร้อนหนาแน่น · มินิมอลใบเดี่ยว · สวนหิน/แคคตัส · ครัวสมุนไพร · ญี่ปุ่นเรียบ
4. ใส่งบ (ไม่บังคับ) + เลือกว่าในบ้าน/นอกบ้าน + ทิศทางแสง
5. **ระบบเสนอเป็นข้อความก่อน** — "แนะนำ 4 ต้น: มอนสเตอร่า 10 นิ้วตรงมุมซ้าย, ..." พร้อมเหตุผลและว่าร้านมีของไหม
6. ผู้ใช้กด **"ดูเป็นภาพ"** → จุดนี้เท่านั้นที่เสียเงินสร้างภาพ
7. แสดงผลเป็น **before/after slider** + รายการต้นไม้ในภาพ (เฉพาะที่ร้านมีจริง)
8. ปุ่ม "ส่งแบบนี้ให้ร้านตีราคา" → `inquiries` intent `design_quote` แนบรายการ + งบ + ลิงก์รูป

**ข้อกำหนดการสร้างภาพ**
- ใช้ **GPT Image 2** โหมด edit/inpaint บนรูปต้นฉบับของผู้ใช้ — **ต้องคงพื้นที่จริงไว้** ห้ามสร้างห้องใหม่ทั้งห้อง
- prompt ประกอบอัตโนมัติจาก: พิกัดที่ผู้ใช้แตะ + ชื่อพันธุ์ + ขนาดกระถาง + สไตล์ + สภาพแสงในรูป
- 1 job = 1 ภาพ (ไม่ทำ 4 ตัวเลือกให้เลือก — ค่าใช้จ่าย ×4)
- ถ้าผู้ใช้ไม่พอใจ ให้แก้ได้ 1 ครั้งโดยนับเป็น 1 quota เพิ่ม
- **ต้องมีลายน้ำ "ภาพจำลอง"** มุมล่างขวาเสมอ — ป้องกันความเข้าใจผิดว่าเป็นรูปจริง
- ลบรูปต้นฉบับของผู้ใช้อัตโนมัติหลัง 30 วัน (§9)

### 7.5 โหมด "งบเท่านี้ อยากได้แบบนี้" (`/budget`)

- อินพุต: งบ (บาท) · สไตล์ · ขนาดพื้นที่ · ในบ้าน/นอกบ้าน · มีสัตว์เลี้ยงไหม
- ระบบจับคู่จาก `species` ที่ `stock_status = in_stock` โดยใช้ `price_range_internal`
- เอาต์พุต: ชุด 3–5 ต้น + ประเมินราคารวมเป็น **ช่วง** ("ประมาณ 3,800–4,500 บาท") ไม่ใช่ตัวเลขเป๊ะ
- ต้องมีข้อความกำกับ: "ราคาประเมินเบื้องต้น ยืนยันกับร้านอีกครั้ง"
- เสนอ 2 ทางเลือกเสมอ: "ชุดตามงบ" กับ "ถ้าเพิ่มอีกนิดได้อะไรเพิ่ม" (upsell แบบไม่ยัดเยียด)

### 7.6 การเลือกโมเดลและแผนทดสอบ

| งาน | ตัวเลือกหลัก | ตัวสำรอง | ราคาอ้างอิง |
|---|---|---|---|
| แชท | **Qwen รุ่นเล็ก** | DeepSeek รุ่นเร็ว | ~$0.03 เข้า / $0.30 ออก ต่อล้าน token |
| วิเคราะห์รูป | **Qwen VL** | Claude (เมื่อต้องการความแม่นสูง) | ~0.3–0.5 บาท/ครั้ง |
| สร้างภาพ | **GPT Image 2** | — | ~1.3 บาท/ภาพ |

**แผนทดสอบก่อนเลือกจริง (ทำก่อนเขียนโค้ด Phase 2)**
1. รวบรวมคำถามจริงจากแชท LINE ของร้าน **30 ข้อ** (ที่บ้านช่วยส่งให้)
2. ยิงเข้าทั้ง Qwen และ DeepSeek ด้วย prompt เดียวกัน
3. ที่บ้านให้คะแนนแบบไม่รู้ว่าอันไหนเป็นของใคร (blind test) 3 ด้าน: ถูกต้อง · ภาษาไทยเป็นธรรมชาติ · น้ำเสียงเหมือนร้าน
4. เลือกตัวที่ชนะ → บันทึกผลไว้เป็นเกณฑ์เปรียบเทียบเวลาเปลี่ยนโมเดลในอนาคต

> ทั้งหมดเรียกผ่าน AI Gateway ตัวเดียว → เปลี่ยนโมเดลได้โดยไม่แก้โค้ด

### 7.7 การคุมต้นทุน (บังคับใช้ในโค้ด ไม่ใช่แค่นโยบาย)

**โควตาต่อคนต่อเดือน**

| ฟีเจอร์ | ไม่ล็อกอิน | สมาชิก | สมาชิกที่เคยซื้อของร้าน |
|---|---|---|---|
| แชทผู้ช่วย | 10 ข้อความ/วัน | 50 ข้อความ/วัน | ไม่จำกัด (มี rate limit) |
| หมอต้นไม้ | 1 ครั้ง | 5 ครั้ง/เดือน | 15 ครั้ง/เดือน |
| สร้างภาพมุมสวน | 0 (ต้องล็อกอิน) | 3 ภาพ/เดือน | 8 ภาพ/เดือน |

> การให้โควตามากขึ้นกับลูกค้าที่เคยซื้อ = เหตุผลให้คนอยากซื้อจากร้าน ไม่ใช่แค่ใช้ฟรี

**เพดานงบระดับระบบ**
- ตั้งค่าใน `/admin/ai-budget`: เพดานบาท/เดือน (ค่าเริ่มต้น 1,000 บาท)
- ใช้ถึง 60% → แจ้งเตือน LINE ที่บ้าน
- ใช้ถึง 85% → ปิดฟีเจอร์สร้างภาพอัตโนมัติ (แพงสุด) แต่แชทยังทำงาน
- ใช้ถึง 100% → ปิดทุกฟีเจอร์ AI แสดงข้อความ "ผู้ช่วยพักชั่วคราว ทักร้านได้เลย" + ปุ่ม LINE
- **ทุกครั้งที่เรียก AI ต้องเช็คเพดานก่อนยิง ไม่ใช่หลังยิง**

**เทคนิคลดค่าใช้จ่าย**
1. **Prompt caching** — ข้อมูลร้านที่ส่งซ้ำทุกครั้ง (system prompt + แคตตาล็อก) ให้ผู้ให้บริการ cache ไว้ ลดค่า input ได้ถึง 90%
2. **แคชคำถามซ้ำ** — คำถามยอดฮิต ("มอนสเตอร่ารดน้ำบ่อยแค่ไหน") เก็บคำตอบไว้ ตอบจากแคชโดยไม่เรียกโมเดล
3. **บีบรูปก่อนส่ง** — 1024px ด้านยาว, JPEG q80 ทำที่ฝั่ง browser
4. **จำกัดความยาวคำตอบ** — max_tokens 400 สำหรับแชท
5. **ตัดประวัติแชท** — ส่งแค่ 6 ข้อความล่าสุด + สรุปของเก่า

### 8.3 หน้าสรุปสำหรับร้าน `/admin/insights`

**บล็อกที่ 1 — ตัวเลขที่ทำเงินได้ (อยู่บนสุดเสมอ)**
- คำค้นที่ไม่เจอผลลัพธ์ 20 อันดับ พร้อมจำนวนครั้งและแนวโน้ม
- ต้นไม้ที่คนกด "ถามร้าน" มากที่สุด
- ต้นไม้ที่คนดูเยอะแต่ไม่กดถามร้าน (= มีปัญหาที่หน้านั้น หรือของหมด)
- ต้นไม้ที่คนเพิ่มเข้า "สวนของฉัน" มากที่สุด

**บล็อกที่ 2 — สุขภาพของเครื่องมือ**
- ผู้ใช้รายวัน/รายเดือน · คนใหม่ vs คนกลับมา
- อัตราคงอยู่ D7 / D30 (บอกตรง ๆ ว่าเครื่องมือมีประโยชน์จริงไหม)
- อัตราคนไม่ล็อกอิน → สมัครสมาชิก
- อัตราเปิดแจ้งเตือน และอัตรากลับมาบันทึกว่ารดแล้ว
- ช่องทางที่คนเข้ามา (Google / LINE / Facebook / ตรง)

**ข้อกำหนดการแสดงผล** — กราฟต้องอ่านออกบนมือถือ, มีตารางข้อมูลดิบให้ดูได้ทุกกราฟ, ระบุช่วงเวลาที่เทียบเสมอ ("เทียบ 30 วันก่อนหน้า")

### 8.4 ฟีเจอร์ต่อยอด (เรียงตามลำดับที่ควรทำ)

| ลำดับ | ฟีเจอร์ | เหตุผลที่จัดลำดับแบบนี้ |
|---|---|---|
| 1 | **ระบบใบเสนอราคาจัดสวน** | ต่อยอดตรงจาก Phase 2 และเป็นงานที่มูลค่าต่อชิ้นสูงสุด |
| 2 | **สแกนหาพันธุ์** | ต่อยอดจากหมอต้นไม้ (ใช้ vision model เดิม) ต้นทุนเพิ่มน้อย |
| 3 | **ระบบแชทของเราเอง** | ทำเมื่อ LINE เริ่มไม่พอ (แนบใบเสนอราคา/รูปหลายใบไม่สะดวก) |
| 4 | **ชุมชนคนรักต้นไม้** | สร้าง retention ดีที่สุด แต่ต้องมีคนดูแลเนื้อหา — ทำเมื่อมีคนใช้พอ |

**ต้นทุน Phase 3**: ค่าระบบ ~2,500–4,000 + ค่า AI ~3,000–5,000 + ค่าแอปเฉลี่ย ~275 = **~6,000–9,000 บาท/เดือน**

## 9. ความปลอดภัยและ PDPA

### 9.1 ข้อมูลส่วนบุคคลที่เก็บ

| ข้อมูล | เก็บทำไม | เก็บนานแค่ไหน |
|---|---|---|
| ชื่อ · รูปโปรไฟล์ · LINE user ID | ระบุตัวตน + ส่งแจ้งเตือน | จนกว่าจะลบบัญชี |
| อีเมล | ล็อกอินสำรอง · กู้รหัสผ่าน | จนกว่าจะลบบัญชี |
| รูปที่ผู้ใช้อัปโหลด (ต้นไม้ · พื้นที่ในบ้าน) | วินิจฉัย · ออกแบบ | **ลบอัตโนมัติ 30 วัน** |
| ประวัติแชทกับ AI | ต่อบทสนทนา · ปรับปรุงคำตอบ | 90 วัน แล้วเก็บเฉพาะสรุปที่ไม่ระบุตัวตน |
| ข้อมูลต้นไม้และการดูแล | ฟีเจอร์หลัก | จนกว่าจะลบบัญชี |

> **รูปพื้นที่ในบ้านคือข้อมูลอ่อนไหว** — เห็นภายในบ้านลูกค้า ต้องเก็บใน private blob, เข้าถึงด้วย signed URL อายุสั้น, ไม่ index, ลบอัตโนมัติ

### 9.2 สิ่งที่ต้องมี

- หน้า **นโยบายความเป็นส่วนตัว** ภาษาไทย (บังคับ ทั้ง PDPA และการขึ้นสโตร์)
- **ขอความยินยอมแยกเรื่อง**: (ก) ใช้งานระบบ (ข) รับแจ้งเตือน (ค) ส่งรูปให้ผู้ให้บริการ AI ประมวลผล
- **ปุ่มลบบัญชี** ที่ลบข้อมูลจริงภายใน 30 วัน (Apple บังคับ + PDPA ให้สิทธิ์)
- **ปุ่มดาวน์โหลดข้อมูลของฉัน** (JSON)
- ระบุชัดในหน้านโยบายว่าใช้ผู้ให้บริการ AI รายใด และข้อมูลถูกส่งออกนอกประเทศ

### 9.3 ความปลอดภัยทางเทคนิค

| ด้าน | มาตรการ |
|---|---|
| Secret | อยู่ใน environment variables ฝั่ง server เท่านั้น ไม่มีใน bundle ฝั่ง client |
| สิทธิ์ | ตรวจ `role` ทุก endpoint ของหลังบ้าน · ตรวจ ownership ทุกครั้งที่แตะ `user_plants` |
| อัปโหลดไฟล์ | จำกัดชนิด (jpg/png/webp) · ขนาด ≤ 8MB · สร้างชื่อไฟล์ใหม่เสมอ · ตรวจ magic bytes ไม่เชื่อ extension |
| Rate limit | ต่อ IP และต่อผู้ใช้ ทุก endpoint ที่เขียนข้อมูลหรือเรียก AI |
| Prompt injection | ข้อมูลจากผู้ใช้ใส่ในบล็อกที่ระบุชัดว่าเป็นข้อมูล ไม่ใช่คำสั่ง · โมเดลไม่มีสิทธิ์เขียน DB โดยตรง (ทุก tool ตรวจสิทธิ์ฝั่ง server) |
| Webhook LINE | ตรวจ signature ทุกครั้ง |
| Cron | ป้องกันด้วย secret header |
| สำรองข้อมูล | Postgres point-in-time recovery + export รายสัปดาห์ |

## 11. แผนทดสอบและเกณฑ์ยอมรับงาน

### 11.1 ระดับการทดสอบ

| ระดับ | ครอบคลุมอะไร | เครื่องมือ |
|---|---|---|
| Unit | **Care Schedule Engine เป็นอันดับแรก** — ตัวคูณ, การปัดเศษ, ขอบเขต 1–30 วัน, เปลี่ยนฤดู, รดก่อน/หลังกำหนด | Vitest |
| Integration | สร้าง task ไม่ซ้ำเมื่อ cron รันซ้ำ · merge guest → บัญชี · สิทธิ์เข้าถึงข้าม user | Vitest + DB ทดสอบ |
| E2E | 5 เส้นทางหลัก (§11.2) | Playwright |
| Manual | ทดสอบบนเครื่องจริง: iPhone Safari, iPhone PWA, Android Chrome | มือ |

### 11.2 เส้นทางที่ต้องผ่าน (E2E)

1. ค้นหา → เปิดหน้าต้นไม้ → กดถามร้าน → ตรวจว่าลิงก์ LINE มีชื่อต้นและ ref code ถูกต้อง
2. สมัครด้วย LINE → เพิ่มต้นไม้ → เห็นตารางดูแล → กด "รดแล้ว" → รอบถัดไปเลื่อนถูกต้อง
3. Guest บันทึกต้นไม้ 3 ต้น → ล็อกอิน → ข้อมูลย้ายเข้าบัญชีครบ
4. แอดมินเพิ่มพันธุ์ใหม่ + รูป + สูตรดูแล → เห็นในหน้าค้นหาสาธารณะภายใน 1 นาที
5. ค้นคำที่ไม่มีในระบบ → เห็นปุ่มถามร้าน → มีแถวใน `search_misses`

### 11.3 เกณฑ์ยอมรับก่อนเปิดตัว Phase 1

- [ ] มีพันธุ์ที่ published พร้อมรูปจริงอย่างน้อย **30 พันธุ์**
- [ ] ทุกพันธุ์มีสูตรดูแลครบ 3 ฤดู
- [ ] Lighthouse บนมือถือ: Performance ≥ 85, Accessibility ≥ 95, SEO ≥ 95
- [ ] ทดสอบบน iPhone จริง (ทั้ง Safari และแบบ Add to Home Screen) และ Android จริง
- [ ] แจ้งเตือนส่งได้จริงทั้ง Web Push และ LINE
- [ ] ที่บ้านเพิ่มพันธุ์ใหม่ 1 ตัวได้เองโดยไม่ต้องถาม ภายใน 5 นาที
- [ ] มีหน้านโยบายความเป็นส่วนตัว
- [ ] มีการสำรองข้อมูลอัตโนมัติและทดสอบกู้คืนแล้ว 1 ครั้ง
